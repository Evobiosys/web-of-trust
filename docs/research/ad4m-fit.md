# AD4M fit assessment — research note (not a decision record; append to DECISIONS.md separately if adopted)

Status: research only, no code changes. Untracked file (not committed) per task instruction — `git add` this deliberately if it should persist.

Scope: does AD4M (github.com/coasys/ad4m) fit our web-of-trust resource-sharing project, is there an obvious low-cost integration now, and — Jakob's hard constraint — is a non-Holochain path real or theoretical.

---

## 1. AD4M in 10 lines (their ontology → our nouns)

1. **Agent / DID** — a sovereign local runtime + persistent DID keypair. ↔ our `did:peer:2` `Identity` (`packages/transport/src/did_identity.ts`): same idea (self-certifying, no ledger), different DID method (AD4M mints its own DID scheme via the "agent-language"; we use `did:peer:2` directly). Not a drop-in match — see §2.
2. **Language** — a pluggable protocol/adapter that stores and syncs *Expressions* or *Links* over some backend (Holochain, IPFS, HTTP, Matrix, ActivityPub, Nostr, Solid, Git…). ↔ our `TransportAdapter` interface (`packages/protocol/src/transport_adapter.ts`, I5 seam) — structurally the closest match in the whole framework: both are "the one coupling point a concrete backend plugs into."
3. **Perspective** — an agent's private, subjective RDF-triple graph (their "Links": `<source> <predicate> <target>`). ↔ our per-persona second-brain graph / SQLite store (items, listings, trust edges) — same idea (locally-owned semantic graph), different data model (RDF triples vs. our zod-typed relational rows).
4. **Neighbourhood** — a *shared*, collaboratively-synced Perspective, addressed by a Language + a Perspective + a Social DNA. ↔ our trust circle / shared room (`createSharedRoom` in `TransportAdapter`, and the D13 3-party relay room) — both are "the group of peers who see a given slice of graph," but Neighbourhoods sync a *whole graph* continuously; our rooms carry discrete signed envelopes (REQUEST/STATUS/CONSENT/LISTING/LOAN/DM). Different consistency model, not just different name.
5. **Social DNA** — SHACL-shaped rules + Subject-class definitions that govern what a Neighbourhood accepts/how it structures itself (a schema + light governance layer, evaluated by an embedded Prolog engine in the executor). ↔ our `SharePolicy`/`TrustLevel`/tier system (`schemas.ts`: audience, mode, requires, tier gates in D14) — same *purpose* (policy-govern what crosses a boundary), radically different mechanism (SHACL/Prolog validation of a shared graph vs. our imperative `evaluatePolicy` gate evaluated per-send against a private trust-edge list). AD4M's Social DNA governs a *shared, replicated* graph; ours governs a *point-to-point send decision* — this is the single largest architectural mismatch (see I1/I2/I3: our asker-blindness and indistinguishable-no invariants depend on the owner's data *never entering* a shared structure pre-consent; a Neighbourhood's whole model is a converging shared graph).

**Headline tension:** AD4M's Neighbourhood/Perspective-sync model assumes members converge on a shared replicated graph (CRDT-like link sets, `p-diff-sync`). Our I1 (local sovereignty) and I3 (indistinguishable no) invariants are built on the *opposite* assumption — nothing enters a multi-party structure until consent, and non-matches are wire-silent. Using a Neighbourhood as our transport would mean either (a) never putting pre-consent state into it (reducing it to a dumb message bus — at which point it's doing no more than our TransportAdapter already does), or (b) redesigning I1–I3 around eventual-consistency graph sync, which is a protocol rewrite, not an integration.

## 2. Non-Holochain viability

**Bottom line: real, not theoretical, and moving fast.** [confidence 0.85]

- The framework's Language interface is explicitly backend-agnostic by design; docs describe Holochain/IPFS/HTTP/Solid as interchangeable substrate choices, not requirements [A: docs.ad4m.dev/languages, accessed 2026-07-18].
- Official templates exist for both DNA (Holochain) and **non-DNA** Language variants (`ad4m-expression-language-template`, `ad4m-link-language-template` — TypeScript/Rollup/Deno-ESM, unit+E2E tests, GH Actions CI; last pushed 2026-06-12 and 2026-05-25 respectively) [A: github.com/coasys, accessed 2026-07-18]. [confidence 0.8]
- The `coasys` org currently hosts a **large, very recently pushed** set of non-Holochain Link Languages — most pushed 2026-07-13/14, i.e. days before this research (today 2026-07-18): `matrix-link-language`, `solid-link-language`, `ap-link-language` (ActivityPub), `atproto-link-language`, `ipfs-link-language`, `nostr-link-language`, `hypercore-link-language`, `git-link-language`, `nextgraph-link-language`, `anytype-link-language`, `peer2panda-link-language` (p2panda over iroh/QUIC — **not** Holochain), plus an older `centralized-socket-link-language` (2023). A companion repo `ad4m-wind-tunnel` ("performance benchmarks + multi-device integration tests for Link Languages — Holochain, ActivityPub, AT Protocol, Nostr, Matrix, Solid, IPFS, Hypercore, Git") was pushed 2026-07-14 [A: GitHub API `search/repositories?q=org:coasys+language`, accessed 2026-07-18]. [confidence 0.85 these are real, functioning; confidence 0.4 they are production-hardened given the compressed push timeline — this reads like a recent, possibly single-contributor sprint, not years of battle-testing]
- **`matrix-link-language` is directly relevant**: it re-implements Perspective/link sync over a Matrix homeserver's native state-resolution DAG (links as `m.room.state` events, OR-Set tombstone semantics, no Holochain). README claims "production-ready" with a verified 2-executor, 20-link, 1.05s sync against a live Conduit homeserver, plus native-Element-client projection via a SHACL-driven transformer [A: github.com/coasys/matrix-link-language README, accessed 2026-07-18]. [confidence 0.55 on "production-ready" self-claim — unverified independently, no third-party adoption evidence found]
- **The AD4M *core* itself ships centralized, non-Holochain bootstrap-language alternatives**, not just third-party Link Languages: `coasys/ad4m`'s `bootstrap-languages/` directory contains `centralized-agent-language` and `centralized-p-diff-sync` sitting alongside the default Holochain-backed `agent-language` and `p-diff-sync` [A: `gh api repos/coasys/ad4m/contents/bootstrap-languages`, accessed 2026-07-18 — direct repo listing, not docs prose]. The executor exposes a `--bootstrapLanguage`-style config surface to select which set loads [A: docs.ad4m.dev/developer-guides/cli, accessed 2026-07-18; exact flag semantics not independently verified — narrative docs don't spell out the centralized swap step-by-step]. [confidence 0.75 that a config-only non-Holochain executor boot is possible; 0.4 that it's a *documented, one-line* switch rather than requiring executor-source-level wiring]
- Recent core development (v0.12.0, March 2026) replaced Holochain's own p2p transport internals with **Iroh** (QUIC-based), described by Holochain's own team as new networking, not an AD4M-specific de-Holochainification — but it signals the whole stack (Holochain included) is moving toward more conventional p2p transport, narrowing (not widening) any Holochain-specific lock-in surface over time [B: Holochain blog + coasys release notes via WebSearch, accessed 2026-07-18].
- **No existing DIDComm Language.** None of the ~15 Link Languages found target DIDComm specifically. A custom "DIDComm Language" is not "pick one off the shelf" — it is new code, using the official non-DNA link-language template as scaffold.

**What a custom "DIDComm Language" would take**, based on the `ad4m-link-language-template` structure [A: template README, accessed 2026-07-18]:
- Implement two adapters: a **Transport Adapter** (wraps HTTP fetch in the template; would wrap our existing `DidCommTransport.send`/`onEnvelope` instead) and a **Storage Adapter** (executor KV store — trivial, already templated).
- Implement `performSync()` (pull/apply remote link deltas) and a commit/push handler (send local links out) — this is the part that has no ready analog in our codebase today, because our TransportAdapter moves discrete signed *envelopes*, not a continuously-converging *link set*. Bridging the two models (envelope stream ↔ synced graph) is the actual engineering content, not the adapter boilerplate.
- Template explicitly separates pure business logic from the executor runtime so it's unit-testable with Deno/Node outside AD4M — lowers integration risk somewhat.
- Rough estimate: **8–15 person-days** for a minimal, alpha-honest DIDComm Link Language (identity mapping did:peer:2 ↔ AD4M DID, sync loop, no UI) by someone already fluent in both our `didcomm_transport.ts`/`vrc.ts` and AD4M's Language interface; add 5–10 days if it also needs to satisfy I1/I3 (i.e., not naively syncing pre-consent state into a shared Perspective — see §1 tension). [confidence 0.5 — estimate, not measured]

## 4. Recommendation

**Option (a) now; keep (b) as a cheap, well-scoped future task; do not pursue (c) at the current milestone.**

AD4M's *Language* abstraction is a genuine architectural cousin of our `TransportAdapter` (I5) — validating that our swap-seam design pattern is not idiosyncratic is useful, and worth one sentence in a future pitch deck. But AD4M's actual value proposition (Neighbourhoods = converging shared Perspectives, Social DNA = shared-graph governance) solves a different problem than ours. Our privacy model is built on *withholding* state from any shared structure until consent (I1–I3); AD4M's is built on *converging* state into a shared structure as the default mode. Forcing our protocol onto AD4M's Neighbourhood model isn't a transport swap (which D12/TRANSPORT.md §7 already scoped cleanly for DIDComm) — it's a redesign of the invariants that make this project's demo distinctive. That cost is not justified by anything in the current milestone (M0–M5, OpenVTC-before-Matrix per D12).

Non-Holochain viability, separately, is **not the blocker it might have been six months ago** — Jakob's constraint is satisfiable today via either a third-party Link Language (Matrix, IPFS, ActivityPub, Nostr, etc. all exist and are freshly maintained) or the framework's own centralized bootstrap-language path. That derisks option (c) *if* the project ever wants it later; it does not make (c) cheap or currently warranted.

**Honesty notes:**
- Core `coasys/ad4m` itself is genuinely active (commits into July 2026, pre-release versions being cut regularly) — **not dormant**.
- But the *specific* non-Holochain Link Language ecosystem that makes Jakob's constraint easy to satisfy is suspiciously fresh: ~10 of the ~15 alternative-backend Link Languages were pushed within a 2-day window (2026-07-13/14), days before this research. That pattern (many repos, one tight window) reads as one push/sprint by a small number of contributors rather than years of independent community adoption — treat "production-ready" self-descriptions (e.g. matrix-link-language's README) as unverified vendor claims, not third-party-confirmed maturity. ⚠️
- Some older Language repos in the same org (`direct-message-language`, `https-language`, `agent-language` standalone repo) are 2-3 years stale with zero community engagement — the ecosystem is uneven: a few actively-maintained core pieces plus a long tail of abandoned experiments. Don't assume every repo under `coasys/` is current.
